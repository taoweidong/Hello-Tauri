## 〇、架构约束与优化原则（重要）

本报告的优化方案统一遵循用户明确的架构约束：

- **业务代码尽量使用 TypeScript**；
- **非必要时不引入 Rust**；
- **Rust 仅负责客户端打包（编译产物）与功能透传**——只暴露底层原子能力（如读写字节、解压字节流），不做业务判定。

由此导出的具体规则：文件名净化、路径穿越防护、压缩炸弹大小上限、格式识别、`.tgz` 的 tar 解包等**业务规则一律放在 TS 层**；Rust 命令保持为"薄透传"原语，最多保留结构性安全边界（如 `write_file` 必须落在 `app_data_dir` 沙箱内），**不实现业务逻辑**。下文各优化方案均按此原则给出。

### B1 🟠 P1 — 固定文件清单校验缺失，未知文件未提示“不支持解压展示”（✅ 已完成，2026-07-28）

> **✅ 完成方式**：新建 `src/core/manifest-validator.ts`（`ManifestValidator` 类 + `manifestValidator` 单例），复用 `archive-manifest.ts` 新增的 `resolveTypeByManifest()` 纯函数（与 `registry.resolveFileType()` 共用同一判定逻辑）；`use-decompress.ts` 在解压成功后调用 `manifestValidator.check(result.files)`，将清单外条目路径写入 `ArchiveItem.unsupportedFiles`；`ArchiveCard.vue` 显示“⚠️ N 个文件不支持解压展示”提示；预览区由已有的 `UnsupportedPlaceholder` 展示占位。

**具体描述**
- 业务要求：解压后文件清单固定，**出现清单外的未知文件时应提示"不支持解压展示"**；缺失可选文件属正常。
- 现状：`src/core/file-validator.ts:46-96` 的 `ZipContentValidator` **仅校验必需文件是否存在**（默认 `['VERSION.txt']`），**没有维护"允许文件清单"白名单**，不会对多出的未知文件做任何拦截或提示。
- 未知文件进入解析链路后，`hexPlugin.canParse()` 返回 `true`（`hex-plugin.ts:53-55`），`safeParse` 失败时也**静默回退为 hex 展示**（`registry.ts:180-187`），与业务要求**完全相反**。

**影响**：业务硬性规则未落地；未知/异常文件被伪装成"可展示"（hex），误导用户。

**优化方案**
- **优化目标**：在解压/校验阶段对照固定文件清单，对未知文件明确提示"不支持解压展示"。
- **预期效果**：合规压缩包正常展示；含未知文件时给出准确的"不支持"提示。
- **实施建议**（业务规则放 TS）：
  1. ✅ **已完成**：`src/config/archive-manifest.ts` 已定义业务清单（基于后缀/前缀模式，非精确文件名），包含 `nameRules`/`suffixRules`/`prefixRules` 三层规则与 `UNSUPPORTED_TYPE` 常量。
  2. ✅ **已完成（2026-07-28）**：`ManifestValidator` 已新建，对解压条目逐一比对：命中清单→放行并标记类型；未命中→标记 `unsupported`，`ArchiveCard` 显示提示，预览区展示“不支持解压展示”占位组件（`UnsupportedPlaceholder`）。
  3. ✅ 此清单已作为类型识别的唯一配置源（`registry.resolveFileType()` 读取 `ARCHIVE_MANIFEST`，B2/B3/B4 共用）。
  4. ✅ `hexPlugin.canParse()` 已改为返回 `false`，不再无条件兜底（`hex-plugin.ts:53-56`）。
  5. ✅ `src/config/index.ts` 已导出 `archive-manifest`。

#### B2 🟠 P1 — `sample.csv` 与 `sample_table_tree.csv` 无法区分（同后缀不同类型）（✅ 已完成）

**具体描述**
- 业务要求：`sample.csv` = **纯表格展示**；`sample_table_tree.csv` = **表格 + 树形左右联动**。二者**后缀同为 `.csv`，但业务语义不同**。
- 按业务规则「同一种类型前缀相同，后缀不同」，`sample_table_tree.csv` 中的 `_table_tree` 后缀修饰符标识了它是不同类型。

**影响**：`sample.csv` 展示语义错误；违反"一类型=一解析TS+一展示Vue"。

**优化方案**
- **优化目标**：`sample.csv` 纯表格；`sample_table_tree.csv` 表格+树形；各自独立。
- **预期效果**：符合"一类型一TS一Vue"，互不干扰。
- **实施建议**（利用 B1 的 `ARCHIVE_MANIFEST.nameRules`）：
  1. ✅ 在 `archive-manifest.ts` 的 `nameRules` 中，`_table_tree.csv` 优先匹配为 `table-tree` 类型（**特殊名称规则优先于通用后缀规则**）—— **已完成**；

```ts
// src/core/file-dispatcher.ts
import type { Component } from 'vue'
import type { IFileParserPlugin } from '@/plugins/types'
import type { ParsedContent } from '@/types'
import { ARCHIVE_MANIFEST } from '@/config/archive-manifest'

/** 文件类型识别结果 */
export interface FileTypeInfo {
  /** 业务类型标识（如 'csv'、'table-tree'、'log'、'unsupported'） */
  type: string
  /** 匹配的规则来源（用于调试/日志） */
  matchedBy: 'nameRule' | 'suffixRule' | 'prefixRule' | 'none'
  /** 匹配到的具体模式（如 '.csv'、'APPLOG'） */
  pattern?: string
}

/** 调度结果：类型 + 解析数据 + 渲染组件 */
export interface DispatchResult {
  /** 文件类型信息 */
  fileType: FileTypeInfo
  /** 解析后的内容（unsupported 时为 null） */
  content: ParsedContent | null
  /** 对应的 Vue 渲染组件（unsupported 时为 UnsupportedPlaceholder） */
  renderer: Component
  /** 解析耗时（ms） */
  loadTimeMs: number
}

/**
 * 核心文件调度器
 * 职责：文件名 → 类型识别 → 解析器选择 → 渲染器分派
 * 所有下游消费方（PreviewPane、ParserEngine、FileTree 等）均通过此调度器获取结果
 */
export class FileDispatcher {
  constructor(private registry: PluginRegistry) {}

  /**
   * 类型识别：按 ARCHIVE_MANIFEST 优先级匹配
   * 顺序：nameRules → suffixRules → prefixRules → unsupported
   */
  resolveType(fileName: string): FileTypeInfo {
    // 1. 特殊名称规则（最高优先，如 _table_tree.csv）
    for (const rule of ARCHIVE_MANIFEST.nameRules) {
      if (rule.pattern.test(fileName)) {
        return { type: rule.type, matchedBy: 'nameRule', pattern: rule.pattern.source }
      }
    }
    // 2. 后缀规则（主策略：后缀明确的按后缀解析）
    for (const rule of ARCHIVE_MANIFEST.suffixRules) {
      if (rule.pattern.test(fileName)) {
        return { type: rule.type, matchedBy: 'suffixRule', pattern: rule.pattern.source }
      }
    }
    // 3. 前缀规则（补充策略：无后缀文件，同类前缀相同）
    for (const rule of ARCHIVE_MANIFEST.prefixRules) {
      if (rule.pattern.test(fileName)) {
        return { type: rule.type, matchedBy: 'prefixRule', pattern: rule.pattern.source }
      }
    }
    // 4. 未命中任何规则 → 不支持
    return { type: 'unsupported', matchedBy: 'none' }
  }

  /** 根据文件名获取对应的解析插件 */
  getParserFor(fileName: string): IFileParserPlugin | null {
    const { type } = this.resolveType(fileName)
    if (type === 'unsupported') return null
    return this.registry.getParserByName(type)
  }

  /** 根据文件名获取对应的 Vue 渲染组件 */
  getRendererFor(fileName: string): Component {
    const { type } = this.resolveType(fileName)
    if (type === 'unsupported') return UnsupportedPlaceholder
    return this.registry.getParserByName(type)?.getComponent() ?? UnsupportedPlaceholder
  }

  /**
   * 一站式调度：类型识别 + 解析执行 + 结果打包
   * PreviewPane 只需调用此方法，无需关心内部调度逻辑
   */
  async dispatch(fileName: string, data: Uint8Array, options?: Record<string, any>): Promise<DispatchResult> {
    const start = performance.now()
    const fileType = this.resolveType(fileName)

    if (fileType.type === 'unsupported') {
      return { fileType, content: null, renderer: UnsupportedPlaceholder, loadTimeMs: 0 }
    }

    const plugin = this.registry.getParserByName(fileType.type)
    if (!plugin) {
      return { fileType, content: null, renderer: UnsupportedPlaceholder, loadTimeMs: 0 }
    }

    const content = await this.registry.safeParse(plugin, data, options)
    return {
      fileType,
      content: { ...content, pluginName: plugin.name },
      renderer: plugin.getComponent(),
      loadTimeMs: performance.now() - start,
    }
  }
}
```

### S2 🔴 P0 — Gzip 解压路径穿越 + 无炸弹防护（✅ 已解决，2026-07-27 核实）

> **✅ 解决方式**：`src-tauri/src/decompress.rs` 已随 Rust 端重构整体删除。gzip 解压改为 **TS 层 `DecompressionStream` API + `memoryStore` 内存写入**（`gzip-plugin.ts`），不再落盘，路径穿越攻击面已消除；`tauri-adapter.ts` 的 `validatePath()` 额外提供了“拒绝 `..` + `appDataDir` 前缀校验（Windows 大小写不敏感）”的 TS 层结构性边界，符合“业务规则在 TS”原则。
> ✅ **残留风险已解决（2026-07-28）**：gzip 解压已增加累计大小上限防护——读取循环中边读边累计 `totalSize`，超过 `MAX_DECOMPRESS_TOTAL_SIZE`（1GB，与 zip 共用 `plugins/helpers.ts` 共享常量，防护对称）时 `reader.cancel()` 并返回失败；同时 gzip 插件标记 `experimental: true`，不进入上传白名单（见 T4），实际攻击面进一步受限。

**原问题描述（已失效，保留存档）**
- `src-tauri/src/decompress.rs:119-140` 的 `decompress_gzip`：`output_name = file_name.unwrap_or("decompressed")`，随后 `output_dir.join(output_name)` 直接 `File::create` 写入。
- 该路径**未做任何净化**：无 `..`/`\`/控制字符拒绝，无 `canonicalize` 前缀校验（对比 `decompress_zip` 在 `:27-90` 的完整防护）；也**没有** `MAX_TOTAL_SIZE` 累计大小上限（zip 在 `:7` 定义了 1GB 上限，gzip 完全没有）。
- `file_name` 来源于用户文件名：`src/plugins/compression/gzip-plugin.ts:14-21` 从用户上传文件名去掉 `.gz/.gzip/.tgz` 后缀得到 `outputName`，传给 `adapter.decompress(data, 'gzip', outputDir, outputName)` → Rust `decompress_gzip`。
- 若用户文件名为 `../../evil.tgz`，`outputName` 为 `../../evil`，`output_dir.join("../../evil")` 会**逃逸 `output_dir`（进而逃逸 `app_data_dir`）** 进行任意位置写入。

**影响**：在 Tauri 端，恶意/畸形 `.gz/.gzip/.tgz` 文件可导致**任意文件写入**（Zip Slip 同类漏洞）或**磁盘被写满**（gzip bomb，无大小上限）。仅 Tauri 端受影响（Web 端写入内存 Map，key 为文件名无穿越），但属高危必须修复项。

**优化方案**
- **优化目标**：使 gzip 解压具备与 zip 同等级别的路径穿越防护与炸弹防护。
- **预期效果**：消除任意文件写入与磁盘耗尽风险，zip/gzip 防护对称。
- **实施建议**（遵循"业务在 TS、Rust 仅透传"原则）：
  1. **把安全校验从 Rust 上移到 TS 业务层**：新增 `src/core/archive-security.ts`，提供 `sanitizeEntryName(name)`（拒绝 `..`、反斜杠、控制字符）与 `enforceTotalSize(total, limit)`（累计大小上限）。zip 与 gzip 共用同一套 TS 校验，不再依赖 Rust 侧各自实现。
  2. **将 `decompress` Rust 命令重构为透明透传**：入参 `(bytes, format)`，返回解压后的条目 `{ name, bytes }[]`（单文件 gzip 返回长度为 1 的列表），**由 Rust 直接返回字节，不自行决定落盘路径、不对文件名做业务判定**。Rust 仅做"解压字节流"这一原子能力。
  3. **TS 侧负责落盘决策**：`use-decompress` / `cache-fs` 拿到解压结果后，先用 `sanitizeEntryName` 处理每个条目名、用 `enforceTotalSize` 累计校验，再调用 Rust 已有的薄原语 `write_file`；`write_file` 的 `validate_path` 只保留"路径必须位于 `app_data_dir` 沙箱内"的**结构性边界**，不实现任何业务规则。
  4. **`.tgz` 的 tar 解包放在 TS**：当前 gzip 插件把 `.tgz` 当单个 gzip 流解压、不解包内部 tar；应在 TS 层用 JS tar 库（如 `tar-stream` / `pako`+tar 解析）完成，Rust 不参与。明确支持范围：要么 TS 实现 tar 解包，要么在上传/检测阶段提示不支持 `.tgz`。

### P5 🟡 P2 — TaskScheduler `retry()` 边界缺陷（✅ 已完成，2026-07-28）

> **✅ 修复方式**：`task-scheduler.ts` 新增 `runningTasks` Map（id → 任务引用），`processNext` 执行前登记、完成后移除；`retry()` 改为 `queue.find(...) ?? runningTasks.get(id)` 定位任务，**running 任务的原 Promise 也会被 reject**（“任务已重试，原任务已废弃”），消除外部等待者悬挂；旧任务完成后因 Promise 已 settle，其 resolve/reject 被忽略，不会污染新任务结果。

**原问题描述**：`src/core/task-scheduler.ts:74-92` 的 `retry()` 仅对**仍在队列中**的任务有效——若任务已在执行（`running`），`this.queue.find` 返回 `undefined`，原 Promise 不会被 reject，旧任务继续跑，新入队的与旧任务会**重复执行**；且 `retry` 未清理 `promises`/`taskFns` 中 `running` 任务的引用（仅删 `queue`）。

**优化方案**
- **优化目标**：修复重试语义，避免重复执行与状态残留。
- **预期效果**：重试只触发一次、状态一致、无泄漏。
- **实施建议**：✅ 已实施——维护 `running` 任务映射（`runningTasks` Map），`retry` 时可定位并 reject 旧任务 Promise、清理引用。

### T4 🟠 P1 — 上传校验与插件能力矛盾 + 业务格式约束未对齐（✅ 已完成，2026-07-28）

> **✅ 完成方式**：
> - `PluginRegistry` 新增 `getUploadExtensions()`：遍历已注册 compression 插件的 `supportedExtensions`，跳过被禁用与 `experimental` 插件；
> - `ICompressionPlugin` 接口新增 `experimental?: boolean` 标记，gzip 插件标记 `experimental: true`（代码保留但不进上传白名单，符合“业务当前仅要求 .zip”）；
> - `ZipExtensionValidator` 去硬编码：通过模块级 `setUploadExtensionsProvider()` 注入白名单提供者（core 层不直接依赖插件层，避免循环依赖），`main.ts` 启动时注入 `registry.getUploadExtensions()`；未注入时回退 `['.zip']`；
> - 未来新增压缩格式：注册插件即自动进入白名单，零核心改动；`.tgz` 问题随 gzip 不启用而暂不处理（维持原方案结论）。

**具体描述（原问题，已修复）**
- `src/core/file-validator.ts` 的 `ZipExtensionValidator` 硬拒绝除 `.zip` 外的所有扩展名，提示"当前仅支持 .zip"。
- 但项目已存在 `gzip` 插件（支持 `.gz/.gzip/.tgz`，`src/plugins/compression/gzip-plugin.ts:8`），设计文档更规划了 7z/rar 插件。
- **业务场景明确**："上传的压缩文件格式固定"——当前业务仅要求 `.zip`，gzip 等格式属于**超前实现但业务未要求**的能力。
- 此外 `.tgz` 经 gzip 插件解压后仅得到**单个解压流**，并不会解包内部 tar（与"压缩包"语义不符），属功能不完整。

**影响**：gzip 插件虽已实现但业务不需要，造成"设计承诺与实现矛盾"的困惑；上传校验硬编码 `.zip` 也不利于未来扩展。

**优化方案**
- **优化目标**：上传白名单与**业务实际要求**对齐，同时为未来扩展预留机制。
- **预期效果**：当前仅允许 `.zip`（符合业务）；未来新增格式时零改动即生效。
- **实施建议**：
  1. ✅ **已完成（2026-07-28）**：`.zip` 仍为当前唯一允许的上传格式（与业务场景一致），硬编码已改为**由插件注册表动态生成**（`registry.getUploadExtensions()` + provider 注入）；
  2. ✅ **已完成（2026-07-28）**：gzip 插件代码保留但标记 `experimental: true`，不进入上传白名单，待业务明确需要时去掉标记即可启用；
  3. **`.tgz` 问题**：当前不启用 gzip 上传，`.tgz` 问题暂不处理；若未来启用，tar 解包在 **TS 层**用 JS tar 库实现（Rust 仅透传 gzip 解压字节，见 S2）。
