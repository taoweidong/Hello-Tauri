## 四、本轮（P1 类型 + P2 收尾）额外修掉的真实缺陷

这几条**不在报告清单里**，是修复过程中顺带暴露的：

| #   | 缺陷                                                                          | 后果                             | 定位方式                            |
| --- | ----------------------------------------------------------------------------- | -------------------------------- | ----------------------------------- |
| 1   | `listInbox` 的日期条件只作用于 `JOIN`，不作用于 `last_content` 子查询         | SQLite 与内存实现结果漂移        | 写收件箱契约测试时发现              |
| 2   | 内存侧 `onlyUnreplied` 条件**写反**（`!== '' \|\| !query.onlyUnreplied`）     | `false` 时不排除无 in 消息的会话 | 契约测试断言双实现等价时发现        |
| 3   | `ControlBar.vue` 的 `placement="bottom-left"` 不在 `Placement` 联合类型内     | 运行期被忽略并回退默认定位       | 类型修复时 vue-tsc 暴露             |
| 4   | `uitest.mjs` 的 `killByName('msedgewebview2.exe')` 杀掉**全机** WebView2 进程 | 误杀用户应用；并发测试互相打架   | 一次并发跑出的「13 个 UI 用例失败」 |

### 缺陷 4 的实测证据（这条最值得记录）

```
基线                                              msedgewebview2 = 6 个（不属于测试脚本）
启动测试实例后                                    msedgewebview2 = 12 个
仅 killTree(pid) 之后                             msedgewebview2 = 6 个  ← 精确回落，无孤儿
```

结论：`taskkill /T /PID` 已完整覆盖 WebView2 子进程，按镜像名扫是**纯误伤**。
修复后改为 `clearStaleInstances()` —— **先探测再动手**，无残留时一个进程都不杀。

## 五、两个「假失败」的根因（都不是代码问题）

修复前 `npm run verify` 会在阶段 2 / 4 间歇性报红，但**代码与用例本身全绿**。
两条根因都不指向业务逻辑，容易被误判成回归：

### 阶段 4：`? 个文件 / ? 个用例通过` 且 1.x 秒失败

**真实原因**：vitest 的 v8 覆盖率 provider 在启动时清空上次的 `coverage/`
（1074 个文件），撞上受限环境的**批量删除保护**：

```
Error: [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":1074,"threshold":50,"targets":["...\\coverage"]}
 ❯ V8CoverageProvider.clean  node_modules/vitest/dist/chunks/coverage.DfSpMS-b.js:4013
```

**取证**：`npm test` 542 用例全绿、`npm run test:coverage` 退出码 0 ——
**只在本编排器里失败**，因为它没给这个子进程传 `CODEBUDDY_SAFE_DELETE_ENABLED=0`
（原实现只给构建与打包传）。

**修复**：① 补上环境变量；② 新增「未跑起来」与「跑了但挂了」的区分判据
（判据：有无 `Test Files` 汇总行），并在失败输出里直接给出出路。
原报告只显示 `?`，把「环境故障」伪装成了「用例失败」。

### 阶段 2：`auto-imports.d.ts` 格式检查间歇失败

**真实原因**：该文件由 unplugin 生成，**恒定输出单行长 type 导出**
（实测连续三次构建 md5 均为 `b83474d3`，是确定性的），而 Prettier 要求折行。
于是形成死循环：格式化 → 下次构建覆盖回长行 → 检查再失败。

**修复**：生成物进 `.prettierignore`（其存在性与条目完整性由 verify **阶段 0** 负责）。

## 七、从本轮固化的三条经验

1. **「断言没有失败」不等于「断言有用」**。新增的 4 条 CSP/控制台断言首跑全绿，
   但绿色可能来自「收集器压根没接上」。做过反证（注入 inline script 与
   `console.error`）才敢确认有效。**凡是「零违规 / 零异常」型断言，都应该反证一次**。

2. **「看起来像回归的失败」先查并发与残留**。本轮的「13 个 UI 用例失败」
   与「阶段 6 打包失败」都不是代码问题，而是两个验证流程同时跑时
   争抢 `msedgewebview2.exe` 与 `dist/`。**验证命令不要并发执行**。

3. **报告里的数字要验口径**。「主 chunk 1.06 MB」与 verify 的「1.01 MB 合计」
   是两个不同口径的指标；前者才是 P-1 要解决的问题。收口时按**原始问题的口径**
   复测（主入口 10.7 KB），而不是拿一个总数宣布「已优化」。
